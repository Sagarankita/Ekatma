# 0B. CROSS-FILE CONSISTENCY LOCK

These rules override any accidental contradictory wording in a later prompt.

## 1. One fact should not be asked twice

Basic Requirements is a **pre-seed** for Adaptive Discovery.

If E04 already captured:

- MIDC / Non-MIDC / Not Sure
- land need / land possession
- new construction
- water need
- power need
- primary business nature
- existing approvals

then E05 must **reuse that answer** and show only the relevant follow-up branch.

Do not ask the entrepreneur the same yes/no question again unless:
- the previous answer was `Not Sure`,
- the answer is missing,
- or the user explicitly chooses to edit it.

## 2. Adaptive question state and data verification state are separate

Adaptive question / branch state:

```text
NOT_VISIBLE
VISIBLE
REQUIRED
ANSWERED
VALIDATED
CONFIRMED
SKIPPED
NOT_APPLICABLE
NEEDS_REVIEW
```

Data verification state:

```text
SELF_DECLARED
USER_CONFIRMED
SYSTEM_VERIFIED
DEPARTMENT_VERIFIED
NEEDS_VERIFICATION
INVALID
EXPIRED
```

Do not use `SELF_DECLARED` as a question state.

Do not treat `NOT_APPLICABLE` as missing information.

## 3. Canonical application states are shared with Department side

```text
DRAFT
READY_TO_SUBMIT
SUBMITTED
FEE_CONFIRMED
DOCUMENT_SCRUTINY
INITIAL_SCRUTINY
TECHNICAL_SCRUTINY
QUERY_RAISED
CORRECTION_REQUIRED
RESUBMITTED
INSPECTION_PENDING
INSPECTION_SCHEDULED
FINAL_DECISION
APPROVED
REJECTED
```

A service may skip inapplicable states.

User-friendly labels such as `Under Review`, `Action Required`, `SLA Risk`, or `Awaiting Entrepreneur Response` are display/queue overlays and must not become conflicting underlying states.

## 4. MIDC is the first detailed department pack, not the system architecture

The Entrepreneur side must remain department-agnostic.

Future department packs may include:
- MPCB
- Fire
- DISH
- Boilers
- Legal Metrology
- local planning authorities
- sector authorities
- other Maharashtra departments

Every new department must plug into the same shared records, generic application shell, document model, query model, inspection model, decision model and dependency graph.

## 5. External department authority boundary

The Entrepreneur side may display every department in one journey.

A department may only decide its own services.

MIDC, MPCB, Fire, DISH and future authorities must never overwrite one another's decision records.

## 6. Current OCR boundary

OCR / automatic document extraction remains a future P2 enhancement.

The current design must work completely using:
- user-entered structured data,
- uploaded documents,
- document metadata,
- verified/reused data,
- approval-generated certificates.

Do not make OCR required in any current prompt.

## 7. AI / RAG boundary

RAG may:
- retrieve
- explain
- cite
- compare
- assist

It does not:
- approve
- reject
- invent legal requirements
- silently change validated regulatory rules

## 8. Baseline regulatory journey ordering

For the agreed A–Z baseline demo:

```text
LAND STAGE
    ↓
MPCB CTE
    ↓
CTE APPROVED / RESOLVED
    ↓
BUILDING / PLANNING
+ PROVISIONAL FIRE where applicable
    ↓
POWER + WATER + CONDITIONAL NOCs
    ↓
CONSTRUCTION / INSTALLATION
    ↓
PRE-OPERATION APPROVALS
```

The rule engine remains configurable for other services, but the Figma demo must not contradict this agreed baseline.
