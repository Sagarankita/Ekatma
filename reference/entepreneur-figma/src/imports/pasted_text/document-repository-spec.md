Create the following new Entrepreneur-side screens in the existing EKATMA system:

* **E11 — Document Centre**
* **E12 — Document Detail / Help**

Do not redesign unrelated existing screens. Only add the components, states, interactions, and prototype links required for these two screens.

---

# E11 — UNIVERSAL BUSINESS DOCUMENT CENTRE

Create a **single universal document repository for the selected business/project**.

The repository must work across all departments and services. Do not create separate document repositories for MPCB, MIDC, Fire, DISH, etc.

## 1. Document Categories

Support these categories:

* Business
* Promoter
* Land
* Project
* Technical
* Building
* Environmental
* Safety
* Previous Approvals
* Professional Certificates
* Declarations
* Inspection-stage Documents
* Other

Use these as filters/categories, not as separate pages.

---

## 2. Document Table / List

Use a dense government-portal-style table/list rather than oversized document cards.

Each document row must show:

* **Document ID**
* **Document Name**
* **Category**
* **Issue Date**
* **Expiry Date**
* **Source**
* **Verification**
* **Validity**
* **Used By**
* **Version**
* **View**
* **Replace**
* **Help**

Allow horizontal organization/column prioritization if needed so the table remains readable.

---

# 3. PRESERVE SEPARATE DOCUMENT STATES

Do **not** combine all document information into one status badge.

Each document must independently represent the following dimensions.

### A. Requirement State

Show one of:

* Required
* Conditional
* Not Required

### B. Availability / Lifecycle

Show one of:

* Missing
* Uploaded
* Processing
* Available

### C. Verification State

Show one of:

* Self-declared
* User-confirmed
* System-verified
* Department-verified
* Needs Verification
* Invalid

### D. Validity

Show one of:

* Valid
* Expired
* Not Applicable

### E. Reuse Attribute

Show:

* Reusable
* Service-specific

### F. Dependency

Show:

* Available now
* Generated by prerequisite approval
* Blocked until prerequisite
* Inspection-stage only

These dimensions should remain visually distinguishable so, for example:

> **Required + Available + Needs Verification + Valid + Reusable**

is possible without being reduced to a single generic “status”.

# 5. UPLOAD ONCE → REUSE WHERE APPLICABLE

Make this a visible product principle within E11:

**UPLOAD ONCE → REUSE WHERE APPLICABLE**

When a document is reusable, show which services currently use it through **Used By**.

Example:

**Used By**

* MPCB — Consent to Establish
* Fire — Application
* DISH — Factory-related service

Do not imply that every document is automatically valid for every department.

Reuse remains conditional on the relevant service requirement and validity/verification state.

---

# 6. GENERATED APPROVAL DOCUMENTS

Documents generated by EKATMA after an approval/decision must automatically become part of this same repository.

Example:

**Approval Certificate**
Source: EKATMA / Department Decision
Verification: Department-verified
Availability: Available
Reuse: Reusable / Service-specific depending on configuration

Do not create a separate “Certificates” repository.

---

# 7. DOCUMENT ACTIONS

### View

Open the selected document / E12.

### Replace

Allow replacement of the current document while preserving its version history.

Do not overwrite the previous version invisibly.

### Help

Open the contextual document-help experience represented by E12 / Regulatory Assistant.

---

# 8. FILTERS / FINDING DOCUMENTS

Add practical filtering for the repository:

* Category
* Requirement State
* Availability
* Verification
* Validity
* Reuse
* Dependency
* Used By / Department

Also provide a document search field.

Keep filters compact and consistent with the existing EKATMA interface.

# 9. DO NOT ADD

Do **not** create:

* Document readiness percentage
* Overall document score
* Artificial “80% complete” indicator
* Separate repositories per department
* New document status model
* New verification model

The repository should communicate the actual document dimensions directly.

# E12 — DOCUMENT DETAIL / HELP

Create a dedicated detail view for one selected document.

This can be a full detail page or the established EKATMA detail/drawer pattern, depending on the existing system.

## 1. Document Header

Show:

* Document ID
* Document name
* Category
* Current version
* Availability
* Verification
* Validity
* Reuse attribute

Keep these consistent with the corresponding E11 row.

---

# 2. DOCUMENT INFORMATION

Provide clear answers to:

### What is it?

Plain-language description of the document.

### Why is it required?

Explain which requirement/service needs it and why it is relevant.

### What should it contain?

Describe the expected contents at a useful level.

### Which GR / rule requires it?

Show the regulatory source where available:

* GR / Rule
* Clause / Section
* Source document
* Effective date where available

If the source cannot be confidently established:

**Needs Verification**

Do not invent a regulatory reference.

### Where is it obtained?

Explain the relevant source/provider/process for obtaining the document where available.

---

# 3. SERVICE USAGE

Create:

## Used By

Show every applicable department/service currently linked to this document.

Example:

| Department | Service                 | Requirement         |
| ---------- | ----------------------- | ------------------- |
| MPCB       | Consent to Establish    | Required            |
| Fire       | Applicable service      | Supporting document |
| DISH       | Factory-related service | Conditional         |

The same document can therefore be understood across the entire business regulatory journey.

---

# 4. REUSABILITY

Show:

**Reuse:** Reusable / Service-specific

If reusable, explain the applicable reuse context rather than implying unlimited reuse.

Example:

> This document can be reused for applicable services while it remains valid and meets the service-specific requirements.

---

# 5. VALIDITY

Show:

* Issue date
* Expiry date
* Current validity
* Verification state

Example:

**Validity:** Valid
**Expires:** 18 Mar 2028

For expired documents, clearly show:

**Expired**

and provide the relevant replacement/update action if applicable.

---

# 6. CONDITIONAL REQUIREMENT

If the document is conditional, explicitly show:

**Requirement:** Conditional

Then explain:

> This document is required only when the relevant business/project condition applies.

Where available, show the triggering condition.

Do not treat a conditional document as universally required.

---

# 7. DEPENDENCY / GENERATED DOCUMENT

If the document is generated by another approval, show:

**Generated by prerequisite approval**

Example:

**Generated by:** Approval / Decision
**Related service:** [Service]
**Approval ID:** [ID]

If unavailable because the prerequisite has not been completed:

**Blocked until prerequisite**

Link back to the relevant Journey / Requirement.

---

# 8. VERSION HISTORY

Create a compact version-history section.

Example:

**Version 3 — Current**
Uploaded: 12 Sep 2026
Verification: User-confirmed

**Version 2**
Uploaded: 04 Aug 2026

**Version 1**
Uploaded: 20 Jul 2026

Actions:

**View version**

Do not silently replace previous versions.

---

# 9. DOCUMENT HELP → REGULATORY ASSISTANT

Add a clear action:

**Ask Regulatory Assistant**

This opens the existing/contextual Regulatory Assistant pattern.

Suggested prompts:

* Why is this document required?
* What should it contain?
* Which GR / rule requires it?
* Where do I obtain it?
* Which services use it?
* Can I reuse it?
* Why is it marked Needs Verification?

The Assistant should explain/retrieve information and provide source context.

It must not turn the document-help screen into a legal approval mechanism.

---

# 10. E11 → E12 PROTOTYPE

From any E11 document row:

**View → E12 Document Detail**

**Help → E12 / Regulatory Assistant context**

From E12:

**Back to Documents → E11**

**Ask Regulatory Assistant → Regulatory Assistant**

**View related requirement/service → relevant E10 Requirement Detail**

**View dependency → E09 Regulatory Journey / E13 Dependency Graph**, where a dependency exists.

Keep these links connected to the existing EKATMA records rather than creating duplicate data.

---

# 11. CORE DATA RELATIONSHIP

The final prototype should communicate this relationship:

**Business / Project**

→ **Universal Document Centre**

→ Document

→ Used By multiple services

→ Linked Requirement(s)

→ Linked Application(s)

→ Linked Approval / Inspection / Compliance records where applicable

The document itself remains a reusable shared record, while each department/service determines how it is required and whether it is applicable.

Do not duplicate the same uploaded document into separate department repositories.
