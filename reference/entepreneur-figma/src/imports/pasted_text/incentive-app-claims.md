Create **E28 — Incentive Application / Claims**.

E28 continues directly from the existing incentive flow:

**E26 Incentives Discovery**
→ **E27 Incentive Detail**
→ **E28 Incentive Application / Claims**

It must also connect naturally to the existing application, document, query, and compliance patterns already established in EKATMA.

**Do not invent a new visual language. Reuse the existing EKATMA Government of Maharashtra interface, including its established header, breadcrumb, typography, spacing, tables, forms, buttons, status badges, borders, colors, and action patterns. Do not use emojis, decorative/AI-generated icons, illustrations, gradients, glassmorphism, or generic SaaS dashboard styling.**

---

# 1. PURPOSE

E28 manages the incentive lifecycle after the entrepreneur decides to pursue a benefit.

It must support the complete lifecycle:

**Discovery**
→ **Benefit Eligibility**
→ **Estimated Incentive**
→ **Eligibility Application**
→ **Department Scrutiny**
→ **Eligibility Certificate**
→ **Periodic Claims**
→ **Claim Verification**
→ **Sanction**
→ **Disbursement**

Do not treat the entire lifecycle as one generic application status.

The entrepreneur should be able to understand whether they are:

* Applying for eligibility
* Already holding an eligibility certificate
* Making a periodic claim
* Waiting for verification
* Correcting a claim
* Awaiting sanction
* Receiving/disbursing an approved benefit

---

# 2. PAGE HEADER

Use the existing EKATMA page structure.

Breadcrumb:

**Dashboard > Incentives > Application / Claims**

Page title:

**Incentive Application / Claims**

Show the selected:

**Scheme**

and, where relevant:

**Benefit**

Also show the associated:

**Business / Project**

Do not create a separate incentive-specific header style.

---

# 3. LIFECYCLE

Represent the configured incentive lifecycle clearly:

**Discovery**
→ **Benefit Eligibility**
→ **Estimated Incentive**
→ **Eligibility Application**
→ **Department Scrutiny**
→ **Eligibility Certificate**
→ **Periodic Claims**
→ **Claim Verification**
→ **Sanction**
→ **Disbursement**

The lifecycle should visually communicate the entrepreneur's current stage.

Do not imply that every scheme necessarily uses every stage if the selected scheme configuration does not include it.

---

# 4. E28 STATES

Support these states:

* **Eligibility Application**
* **Eligibility Certificate**
* **Claim Period**
* **Claim Submitted**
* **Under Verification**
* **Sanctioned**
* **Disbursed**
* **Correction Required**

Use the existing EKATMA status treatment.

Do not create a new incentive-specific status system.

---

# 5. ELIGIBILITY APPLICATION

When the entrepreneur is applying for eligibility, show:

* Scheme
* Selected benefit(s)
* Business / project
* Preliminary eligibility context from E27
* Required information
* Required documents
* Applicable conditions
* Current state
* Submission status

Reuse information already available from:

* Business Profile
* Business DNA
* Master Project Dossier
* E27 benefit eligibility context

Do not ask the entrepreneur to repeatedly enter master business/project facts.

---

# 6. DEPARTMENT SCRUTINY

Show the application moving through department scrutiny using the same general application-processing pattern already established in EKATMA.

Show where applicable:

* Submitted
* Under Scrutiny
* Correction Required
* Eligibility Certificate Issued

Do not create a separate incentive-specific department workflow model.

If the department raises a query/correction, reuse the existing query/correction interaction pattern.

---

# 7. CORRECTION REQUIRED

When the department requires corrections:

Show:

**Correction Required**

Clearly identify what needs to be corrected.

Use the existing EKATMA query/correction patterns rather than creating a new incentive query system.

Where appropriate, connect to:

**E20 Query / Deficiency Response**

and:

**E21 Delta Resubmission**

Do not represent correction as final rejection.

---

# 8. ELIGIBILITY CERTIFICATE

When an eligibility certificate is issued, show:

* **Certificate ID**
* **Scheme**
* **Validity**
* **Eligible Benefits**
* **Conditions**
* **Business / Project**
* **Documents**

Clearly distinguish the eligibility certificate from a periodic claim.

---

# 9. ELIGIBILITY CERTIFICATE DOCUMENT

Where the eligibility certificate is generated by the department/system, it should become part of the existing universal Document Centre.

Relationship:

**Eligibility Certificate**
→ **E11 Document Centre**

Preserve its own document/version identity.

Do not create a separate incentive certificate repository.

Provide:

**View Certificate**

and where appropriate:

**View in Document Centre**

---

# 10. ELIGIBILITY CERTIFICATE CONDITIONS

Show the conditions attached to the eligibility certificate.

Keep:

**Eligible Benefits**

separate from:

**Conditions**

The certificate may cover multiple benefits.

Do not imply that receiving an eligibility certificate automatically means every possible benefit has been sanctioned or disbursed.

---

# 11. PERIODIC CLAIMS

After eligibility is established, support periodic claims.

Show a clear **Claims** section.

For each claim show:

* **Claim Period**
* **Benefit**
* **Claimed Amount**
* **Evidence**
* **Submission Date**
* **Status**
* **Department Comments**
* **Sanctioned Amount**
* **Disbursement**

Use a clean EKATMA-style table.

Do not create oversized claim cards.

---

# 12. CLAIM STATUS

Use the configured E28 states where applicable:

**Claim Period**

**Claim Submitted**

**Under Verification**

**Correction Required**

**Sanctioned**

**Disbursed**

The claim status should describe the claim's actual lifecycle.

Do not show a claim as:

**Disbursed**

until the configured disbursement state has actually been reached.

---

# 13. CLAIM PERIOD

Clearly show the period to which a claim relates.

Example:

**Claim Period:** Apr 2027 – Jun 2027

Do not assume every scheme uses the same claim frequency.

Use the selected scheme's configured claim cycle.

---

# 14. CLAIMED AMOUNT

Show:

**Claimed Amount**

separately from:

**Sanctioned Amount**

Do not automatically equate the two.

If the claim has not yet been sanctioned:

**Sanctioned Amount: —**

---

# 15. EVIDENCE

Show the evidence required for the claim.

Where evidence already exists in the Universal Document Centre:

allow reuse through:

**E11 Document Centre**

Do not create a separate claims document repository.

Preserve document versions when new evidence is uploaded.

---

# 16. DEPARTMENT COMMENTS

Where the department provides comments, show them in the claim detail.

Examples may include:

* Verification comment
* Correction request
* Sanction comment

Do not invent department comments for prototype data if none exist.

---

# 17. DISBURSEMENT

When a claim reaches disbursement, show the relevant disbursement information available to the system.

Keep:

**Claimed Amount**

**Sanctioned Amount**

and:

**Disbursement**

as separate pieces of information.

Do not imply that sanction and disbursement are the same event.

---

# 18. BENEFIT-LEVEL HANDLING

Remember:

**SCHEME ≠ BENEFIT**

A scheme may have multiple benefits.

E28 must therefore preserve the selected benefit context throughout eligibility and claims.

Example:

**Scheme**

→ Benefit A
→ Benefit B
→ Benefit C

A claim should clearly identify:

**Benefit:** Benefit A

Do not merge multiple benefits into one ambiguous claim record.

---

# 19. DOCUMENTS

Use the existing Universal Document Centre.

Relevant documents may include:

* Eligibility certificate
* Supporting evidence
* Claim evidence
* Department-issued documents

Provide:

**View Documents → E11**

and relevant document detail/help:

**E12**

Do not create a separate incentive document system.

---

# 20. SOURCE / ELIGIBILITY CONTEXT

Where useful, retain the relationship to E27:

**Benefit**
→ **Eligibility Conditions**
→ **Eligibility Application**
→ **Eligibility Certificate**
→ **Claim**

The preliminary eligibility information from E27 should not be converted into a final eligibility decision merely because the entrepreneur starts E28.

Final eligibility should be represented by the configured eligibility process/certificate.

---

**View Eligibility Conditions**

**View Conditions**

**Start Claim**

**Upload Evidence**

### Verification stage

**View Claim**

### Correction stage

**Resolve Correction**

### Sanction stage

**View Sanction**

### Disbursement stage

**View Disbursement**

Do not show irrelevant actions.

---

# 22. REGULATORY ASSISTANT

Where the existing Regulatory Assistant is available, provide contextual assistance.

Possible questions:

* What benefit am I applying for?
* What evidence is required?
* Why was this claim marked for correction?
* What does this eligibility condition mean?
* What is the claim period?
* What is the difference between claimed and sanctioned amount?

Use the existing Regulatory Assistant pattern.

Do not create a new chatbot interface.

---

# 23. PROTOTYPE CONNECTIVITY

Connect E28 to the existing EKATMA system:

**E26 Incentives Discovery**
→ **E27 Incentive Detail**
→ **E28 Incentive Application / Claims**

From E28:

**Documents**
→ **E11 Document Centre**

**Document Detail**
→ **E12 Document Detail / Help**

**Correction**
→ **E20 Query / Deficiency Response**

**Delta Resubmission**
→ **E21 Delta Resubmission**

**Eligibility / Application context**
→ Existing application patterns where applicable

**Compliance-related obligations where configured**
→ **E24 Compliance Dashboard**

Do not create a separate incentive-only application, document, query, or status architecture.

---

# 24. STATE CONSISTENCY

The state shown in E28 must remain consistent with the incentive lifecycle.

For example:

If the page says:

**Eligibility Certificate**

do not simultaneously show:

**Eligibility Application Pending**

unless these are clearly represented as separate records/stages.

Similarly:

If a claim is:

**Under Verification**

do not show:

**Sanctioned**

for the same claim.

If a claim is:

**Correction Required**

do not show it as:

**Disbursed**

---

* Page width

* Buttons

# 26. FINAL END-TO-END TEST

The completed incentive journey should communicate:

**E26 Discovery**
→ **E27 Scheme / Benefit Detail**
→ **E28 Eligibility Application**
→ **Department Scrutiny**
→ **Eligibility Certificate**
→ **Claim Period**
→ **Claim Submitted**
→ **Under Verification**
→ **Sanctioned**
→ **Disbursed**

With correction where required:

**Claim / Application**
→ **Correction Required**
→ Existing Query / Correction pattern
→ **Resubmission**
→ Continue lifecycle

E28 should answer:

**“Where am I in the incentive process, what benefit am I pursuing, what documents/evidence do I need, what has the department decided, and what happens next?”**

The entire screen must feel like an integrated extension of EKATMA's existing application and regulatory workflows, not a separate incentive-management product.
